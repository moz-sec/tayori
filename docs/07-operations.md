# 無料枠・運用設計

確認日: 2026-09-29。数値は公式資料によるプラン上限と、本アプリの設計上の予算を区別する。

## 1. Cloudflareの主な上限

| 対象 | Freeの値 | 参照 |
|---|---|---|
| Workers | HTTP/Cron CPU 10ms、10万request/日、128MB | [制限](https://developers.cloudflare.com/workers/platform/limits/) |
| Cron | アカウント5設定 | 同上 |
| Queues | 1万操作/日、保持24時間 | [料金](https://developers.cloudflare.com/queues/platform/pricing/) |
| Queue consumer | 標準CPU30秒、wall time15分という記載。Free実証を先行 | [制限](https://developers.cloudflare.com/queues/platform/limits/) |
| D1 | 読取500万行/日、書込10万行/日 | [料金](https://developers.cloudflare.com/d1/platform/pricing/) |
| D1容量 | 1DB 500MB、アカウント合計5GB | [制限](https://developers.cloudflare.com/d1/platform/limits/) |
| D1実行 | Freeは50クエリ/Worker実行、bind100個/文 | 同上 |
| D1 Time Travel | Freeは7日 | [バックアップ](https://developers.cloudflare.com/d1/reference/time-travel/) |

既存Worker、D1、Queueやステージングも合算する。D1上限到達時はクエリが失敗する。Paidへの変更は月額・従量課金の前提を変えるため、本アプリの予算設定だけを0円保証として扱わない。

## 2. Queue操作の試算

1メッセージ64KB未満、通常成功=write/read/deleteの3操作。tickもカウントする。sendBatchしてもメッセージ単位の操作数は減らない。

| ケース | fetch/日 | tick/日 | 基本操作/日 |
|---|---:|---:|---:|
| 50購読先・60分 | 1,200 | 288 | 4,464 |
| 50購読先・30分 | 2,400 | 288 | 8,064 |
| 100購読先・60分 | 2,400 | 288 | 8,064 |
| 100購読先・30分 | 4,800 | 288 | 15,264 |

初期は50件・60分を採用。30分一律にしない。再試行、重複送信、初回移行、障害回復分は表に含まない。

アプリ側の目安は推計8,000操作/日以下。tickは再試行1回分を含め4×288=1,152操作を先に控除し、fetch送信は1回につき4操作を原子的に予約する。再送も予約し、残り予算がなければ台帳を翌UTC日へ持ち越す。消費は過少集計を避けるため送信失敗でも安易に払い戻さない。

これは概算ガードであり、重複配信・日をまたぐ処理・他アプリ分まで厳密に止める課金装置ではない。Cloudflare実測を併用し、共有枠に合わせて8,000をさらに下げる。

## 3. D1と容量の試算

仮定: 50購読先×10新着/日=500記事/日、保存レコード平均4KiB（索引等を含む仮置き）。通常記事7日分は約13.7MiB。お気に入り等は別途累積する。

識別台帳item_keysを1件200Bと仮定すると年間約36.5MB増える。実際のSQLiteページ・索引で変わるため、DBの実サイズを定期確認する。7日保持でも全DB容量が固定になるわけではない。

fetch関連20行/回、新着記事と索引・識別台帳10行/件、期限削除10行/件という保守的仮置きでは、1,200×20+500×10+500×10=34,000書込行/日。tick・API・ボード・ジョブ掃除は追加。実測meta.rows_writtenで係数を更新する。304でも取得状態更新は書込になる。

ETag非対応サイトで全記事を毎回UPDATEすると、この見積もりを大きく超える。content_hashが同じ記事は書き込まない。

## 4. 停止と保持

設計上の目安: DB350MBで警告、400MBで新規取り込み停止。D1日次書込の運用警戒線60,000行、読取300万行を仮置き。共有枠・実測から調整する。

アプリの予算予約とnew_articles上限、Cloudflareメトリクスによる監視を組み合わせる。メトリクスの遅延があるので即時ハードキャップを約束しない。停止中も既存記事の閲覧と期限整理を可能な範囲で続け、無料枠でDBが拒否されたらUIに利用不可を表示する。

取得失敗は15分→60分→6時間→24時間等へ後退。Retry-Afterがあれば優先し、極端な指定は上限を設ける。購読ごとの取得時間を分散。上限超過フィードは警告し、同じ負荷を無限再試行しない。

## 5. 日常監視

収集成功率、最終成功、最終tick、Queue backlog/age/retry、CPU超過、D1 rows read/written、DB容量を確認。ログにはrequest/job/sourceのID、HTTPステータス、処理時間、エラー種別だけを残す。全文ログ・外部ログ基盤は初期に追加しない。

## 6. バックアップと復元

- D1 Time Travel 7日を短期事故復旧に使う。記事の7日保持とは別機能。
- 週1回とマイグレーション前にD1をSQL exportし、本人のPC等へ保存。自動R2バックアップは初期スコープ外。
- アプリのランタイムはCloudflare内で完結し、バックアップ保管先だけを手元にする。
- エクスポートは書込処理へ影響し得るため、収集とUI更新を一時停止して実施する。外部共有しない。
- 世代保持は4週を設計案とする。7日経過記事がバックアップに残る可能性を明示する。

復元手順: 収集停止→現状を退避→別DBへSQL import→件数・制約・記事状態を確認→ジョブ失効/generation更新→Webとcollectorのbindingを同じ復元DBに切替→動作確認→収集再開。失敗時は旧DBへ戻す。OPMLのみでは既読・ボード・識別台帳は戻らない。

目標はTime Travelが利用可能な通常事故では直前まで復旧、外部SQLのみなら最大7日分の損失。復旧時間は個人運用で固定保証せず、初回リリース前に復元を実演する。

## 7. 費用の境界

独自ドメイン購入料、既存契約の料金、端末/通信料は本アプリのCloudflare使用料とは別。既存ドメインがなければworkers.dev＋Accessを候補とする。公開前にFree契約・支払設定・既存使用量を確認する。有料製品や外部クラウドは必要性が出るまで追加しない。
