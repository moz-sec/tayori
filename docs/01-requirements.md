# 要件定義

## 1. 背景と目的

現在はFeedlyで約50件を購読している。購読数よりもフォルダ数の制限が使いにくいため、自分の分類方法で整理できるアプリを作る。

## 2. 確定要件

| ID | 要件 |
|---|---|
| R-01 | アプリケーション名はTayori |
| R-02 | 利用者は本人1人、初期の購読規模は約50件 |
| R-03 | 少数に固定されたフォルダ数の上限をなくす |
| R-04 | アプリの稼働基盤はCloudflareに統一する |
| R-05 | 原則月額0円。枠内に収めるため取得を遅らせる設計を許容 |
| R-06 | 初期アプリの通常記事の保存期間は7日間固定 |
| R-07 | 保存期間の設定変更は将来対応 |
| R-08 | シンプルなアイコンと使い勝手を重視する |

100件を超える購読は初期の必須条件に含めない。フォルダやボードに3件などのプラン上限は設けないが、名前の長さ、リクエストサイズ、全体容量には技術上の上限を設ける。

## 3. 初期機能（設計案）

| ID | 機能 | 受け入れ条件 |
|---|---|---|
| F-01 | RSS/Atom購読の追加・停止・解除 | 約50件の購読を管理できる |
| F-02 | フォルダ作成・改名・移動・削除 | 10個のフォルダで分類できる |
| F-03 | 全体・フォルダ・購読先ごとの記事一覧 | 未読絞り込み、日時順、続きを読める |
| F-04 | 既読/未読、まとめて既読 | PCとスマートフォンで状態が一致する |
| F-05 | あとで読む、お気に入り | 保存・解除ができ、保存中は期限削除されない |
| F-06 | ボードによる記事整理 | 4個以上作成でき、1記事を複数ボードへ保存できる |
| F-07 | OPML入出力 | フォルダ構造を保ち、重複登録を避ける |
| F-08 | 定期取得と状態表示 | 成功・失敗・停止・最終取得時刻を区別できる |
| F-09 | 自動整理 | 期限を過ぎた通常記事を削除し、同じ記事が再出現しない |
| F-10 | 本人限定アクセス | UI・API・プレビューの迂回経路から他人が利用できない |
| F-11 | データバックアップ・復元 | 購読・既読・保存記事・ボードを復元できる |

## 4. 保存期間の解釈（設計案）

- 初回取得日時から7×24時間とする。公開日時や既読日時からは数えない。
- 期限後の記事は一覧から除外し、5分周期のtickで本文レコードを最大100件ずつ物理削除する。障害が起きた場合は、処理の再開後に削除する。
- 未読も期限対象。あとで読む・お気に入り・ボード所属のいずれかがあれば保持する。
- すべての保存指定を解除した場合、初回取得から7日を過ぎた記事は一覧から除外し、次の整理処理で削除する。
- 再取り込みを防ぐための最小限の記事識別情報は、本文を削除した後も残す。バックアップから削除する場合とは別に扱う。
- 保存記事が増えて容量が不足した場合は新規収集を停止し、保存記事を無断削除しない。

## 5. 初期対象外

RSSのないWebサイトからの記事抽出、ページ差分監視、全文スクレイピング、AI要約、ネイティブアプリ、オフライン閲覧、多人数利用、外部RSSアプリ互換API、画像の永続保存、全文検索、表示形式の切替。

Webサイト監視は将来の候補であり、すでに実装することが確定した要件ではない。

## 6. 非機能要件（目標値）

- PCとスマートフォンのブラウザで利用可能。通常は再取得・画面復帰時に同期し、常時WebSocketは使用しない。
- 標準取得間隔60分。初回移行や障害・無料枠不足時の遅延は画面に表示する。
- RSS/Atomの成功率・CPU・使用量は実際の購読先で検証する。
- 操作失敗時には再試行可能かを表示。成功前の状態を確定表示しない。
- 有料化による自動解決を行わない。
