# 収集監視と通知

毎時の Cron から監視を実行し、直近の tick、収集成功、フィードの連続失敗、
未完了ジョブの滞留、予算による停止を確認する。
通知は障害の発生時と回復時に送り、同じ状態が続く間は繰り返さない。
通知に含めるのは固定の状態名のみで、フィードの URL、記事本文、認証情報、例外の詳細は含めない。

## 設定

ビルド時に環境変数 `TAYORI_MONITORING_ENABLED=true` を指定すると、監視用のバインディングが構成される。
有効にしない場合、監視通知は実行されない。
HTTPS の Webhook URL を Worker のシークレット `MONITOR_WEBHOOK_URL` に設定する。
Webhook は JSON の `text` フィールドを受け取れる必要がある。
URL は認証情報を含み得るため、リポジトリやログに記載しない。

しきい値はビルド時の環境変数として正の整数で指定する。
設定値は `bindings.text` を通じて Worker に渡される。
未指定または不正な値は既定値を使う。

| 変数                            | 既定値  | 意味                                     |
| ------------------------------- | ------- | ---------------------------------------- |
| `MONITOR_TICK_STALE_SECONDS`    | `10800` | 最終 tick からの経過秒数                 |
| `MONITOR_BACKLOG_STALE_SECONDS` | `10800` | 最も古い未完了ジョブの作成からの経過秒数 |
| `MONITOR_FAILURE_THRESHOLD`     | `3`     | 有効なフィードの連続失敗回数             |

初回は監視開始時刻から tick の経過時間を測る。
収集が日次設定でも Cron と tick は毎時動くため、記事の取得がないだけでは停止と判定しない。
最終成功時刻は状態確認に使い、取得間隔が長い正常なフィードを停止と誤判定しないよう、
単独では通知条件にしない。

## 通知と確認

`tick_stale` は tick の遅延、`queue_stale` は未完了ジョブの滞留、
`feed_failures` は連続失敗、`budget_stopped` は予算停止を示す。
`started` が発生、`recovered` が回復を表す。
通知に失敗した場合、通知状態を更新せず、次回の Cron で再試行する。
監視の失敗は収集 tick の送信を妨げない。

通知を受けたら、Worker の実行状況と Queue、D1 の `app_state`、`sources`、`fetch_jobs`、
予算の状態を確認する。確認時も URL や記事などの非公開情報を外部に転記しない。
原因を解消した後、次回の監視で回復通知を確認する。

この監視は同じ Worker と D1 に依存する。
Cron 自体が停止した場合、D1 にアクセスできない場合、通知先に到達できない場合は、
この仕組みだけでは通知できない。
Cron や Worker 全体の停止を検知するには、独立した外部監視が別途必要になる。
同時に実行された監視が同じ過去の状態を読んだ場合、同じ通知を複数回送ることがある。
通知先が受け取った後に通信が失敗した場合や、送信後の状態保存が失敗した場合も、
次回の再試行で通知が重複することがある。
無料枠内での運用を想定するが、実際の利用量と通知先の料金は各サービスで確認する。

## テスト

`npm run test -w @tayori/collector -- --run src/monitoring.test.ts` で発生、継続時の抑止、回復、
通知失敗後の再試行、機密情報を含めないことを確認できる。実際の Webhook には送信しない。
