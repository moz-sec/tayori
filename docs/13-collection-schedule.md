# RSS収集スケジュール

Issue #26の設定・適用方法。保存期間は引き続き7日固定で、この設定からは変更しない。

## 設定と画面

サイドバーの「RSS収集設定」から、全購読先に共通する設定を変更する。

- 取得間隔：1・2・3・6・12・24時間。未設定時は1時間。
- 毎日の実行時刻：日本時間の0:00〜23:00、1時間単位。
- タイムゾーン：Asia/Tokyo固定。

画面には保存済み設定と、有効な購読先のうち最も早い次回取得予定を表示する。フォームの編集値は保存成功まで確定表示しない。保存失敗時は入力値を保持してエラーを表示する。ダイアログを開き直すとD1から設定を取り直すため、
別端末で保存した設定も確認できる。

記事一覧の「更新」、ページ表示、設定保存はRSSを即時取得せず、新規取得ジョブも作成しない。購読登録時の初回取得は従来の別処理を維持する。

## APIと永続化

`GET /api/v1/settings/collection-schedule` で設定を取得し、同じパスの `PUT` で保存する。Cloudflare Access認証、同一Origin、
application/jsonの制約を通常APIと共用する。リクエストは4KBまで。

```json
{
  "mode": "interval",
  "interval_hours": 6,
  "daily_hour_jst": 0,
  "timezone": "Asia/Tokyo"
}
```

4項目はモードにかかわらず必須。日次モードは `mode: "daily"` とする。レスポンスは `{ "data": { ...設定, "next_fetch_at": "ISO 8601 UTC または null" } }`。
有効な購読先がない場合、次回予定はnull。不正入力は400で保存しない。OpenAPIにも仕様を登録している。

D1の `app_state` の `collection_schedule` キーに設定JSONを保存する。設定の保存と、全購読先の `next_fetch_at` の再計算を同一D1 batchで実行する。
どちらかが失敗したら両方ロールバックする。既存記事や記事キー、既読・お気に入り・あとで読むは変更しない。

## 時間境界と適用

CollectorのCronは毎時00分を維持する。間隔モードの基準はUTC epochで、設定された時間数の倍数になる次の時間境界へ揃える。例えば6時間間隔はJST 03:00・09:00・15:00・21:00。
保存直後の最初の待ち時間は指定間隔より短くなる場合がある。日次モードは保存時刻より後の、最初のJST指定時刻を選ぶ。

Collectorは処理完了時刻に間隔を足さず、時間境界から次の予定を計算する。Queue待ちによる数分の遅延が次の間隔を延ばさない。予定は取得開始の目安であり、Queue待ちやRSS応答の遅延により取得完了は遅れる。

設定変更時、pending・sent・runningのジョブは取り消さず、一度完遂してから新しい予定へ移る。保存そのもので追加ジョブは作らない。処理中に設定が変更された場合、完了したジョブは保存し直された次回予定を上書きしない。
Collectorはジョブ作成時にも設定スナップショットをSQLで照合する。

## 失敗・遅延・重複

失敗時は既存の段階的待機とRetry-Afterを守る。次回取得は、定期収集の予定と失敗後の待機期限の遅い方になる。`sources.retry_not_before` に独立した待機期限を保存し、設定変更でも短縮しない。
日次設定で失敗した場合も、通常は次の日次予定まで待つ。待機期限がその予定を越える場合、期限後の毎時Cronで再試行する。

古い時間帯の遅延tickは破棄し、現在の時間帯のtickで期限超過の購読先を1回だけ取得する。過去の予定の回数分を再実行しない。既存の有効ジョブ一意制約、generation検証、Queue予算予約、
記事キー・content_hashによる重複排除を維持する。

## 導入と確認

既存D1には `migrations/0002_collection_schedule.sql` をApp/Collectorの更新より先に適用する。失敗中の既存購読先については、現在の `next_fetch_at`
を待機期限として引き継ぐ。設定がない場合や保存値が壊れている場合は毎時間隔で動作する。

ローカルではルートの `npm run db:migrate:local`、対象環境では既存の環境別マイグレーション手順を使う。本番・Previewの環境変数やDB IDを混在させない。
ローカルテストは全マイグレーションを適用したSQLiteで、API保存・ロールバック・入力検証・次回境界・実行中変更・再試行・重複tickを確認する。画面操作の実ブラウザーテストは、Issue #38の後続PRで整備する。
